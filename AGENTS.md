# Mewting — Agent Instructions

Read docs/MASTER_SPEC.md before implementing changes.

## Rules
- Follow the required technology stack.
- Use TypeScript.
- Keep the architecture lightweight.
- Develop for Windows native Node.js.
- Do not introduce Docker, Podman, or Kubernetes.
- Implement one milestone at a time.
- Do not remove existing working features.
- Validate incoming realtime events.
- Never hardcode credentials.
- Never claim tests passed unless executed.

## Verification
- Run available typechecks and builds.
- Fix errors introduced by your changes.
- Report tests executed and remaining issues.

## Development
- Follow the milestone order in MASTER_SPEC.md.
- Prefer simple, maintainable code.
- Update README when setup instructions change.

## AI Attribution & Branding Rules

- Do not add AI-generated attribution, signatures, or branding to project files.
- Do not include phrases such as:
  - "Generated by Codex"
  - "Created with OpenAI"
  - "AI-generated code"
  - "Implemented by an AI assistant"
  - "Co-authored-by: Codex"
- Do not add AI attribution footers to README files, documentation, source code, or configuration files.
- Do not include AI-related signatures or promotional text in Git commit messages.
- Keep commit messages concise, professional, and focused on the actual changes.
- Do not add unnecessary comments explaining that code was generated or modified by AI.
- Do not introduce AI branding into the application's UI, metadata, or package information.
- Preserve existing copyright notices, license requirements, and legally required attribution.
- Do not falsify authorship or remove attribution required by third-party licenses.
- Keep implementation summaries focused on technical changes, validation results, and Git status.

## Git Commit Identity

- Use the repository's existing Git author configuration.
- Do not automatically add AI tools as Git co-authors.
- Do not modify the configured Git username or email without explicit permission.
- Never impersonate another contributor.

## Git Workflow Rules

- Always work on the existing `feat/initial-setup` branch during MVP development.
- After completing each requested task, validate the changes before committing.
- Run relevant tests, TypeScript checks, and build commands when available.
- If validation fails, fix the issues before committing.
- After successful validation, automatically create a Git commit and push it to `origin/feat/initial-setup`.
- Use descriptive Conventional Commit messages:
  - `feat: ...` for new features
  - `fix: ...` for bug fixes
  - `refactor: ...` for code improvements
  - `docs: ...` for documentation updates
  - `chore: ...` for maintenance
- Stage only files related to the current task.
- Never commit secrets, `.env` files, credentials, or `node_modules`.
- Never use `git push --force`.
- Never discard existing uncommitted changes without explicit permission.
- If a push fails, report the error instead of silently skipping it.
- Do not create a new branch unless explicitly requested.
- At the end of each task, report:
  - Files changed
  - Validation results
  - Commit hash
  - Push status

Commit and push automatically after each successfully completed task without requesting confirmation again, provided the environment permits Git operations.
