# MEWTING v0.1 — MASTER DEVELOPMENT PROMPT

## ROLE

You are a Senior Full-Stack Engineer, Realtime Systems Architect, and 2D Game Developer.

Your task is to design and implement **Mewting**, a lightweight, cozy, browser-based multiplayer virtual meeting space.

Build a functional application, not just a UI mockup, conceptual prototype, or technical documentation.

Prioritize correctness, simplicity, maintainability, and working realtime communication over unnecessary visual complexity.

## 1. PRODUCT OVERVIEW

**Product Name:** Mewting  
**Tagline:** A Cozy Place to Meet  
**Platform:** Desktop web browser  
**Development Environment:** Windows 10/11, native Node.js  
**Deployment Target:** Local development first; container-ready for future deployment.

Mewting is a lightweight alternative to Gather Town.

Users appear as cute, customizable blob-cat mascots inside a shared virtual environment. They can move between rooms, interact with other users, communicate through realtime text chat, and participate in voice calls.

The visual design should be minimal, cozy, and playful.

## 2. CORE FEATURES (MUST IMPLEMENT)

### 2.1 Player Identity

- Users enter a nickname before joining.
- Users select a blob-cat mascot color.
- Generate a unique player ID.
- No registration or login required.
- Persist nickname and color locally.
- Never trust client-provided player IDs for authorization.

### 2.2 Multiplayer

- Multiple users can join the same virtual environment.
- Display all players currently inside the same room.
- Support WASD and arrow-key movement.
- Synchronize player positions using Socket.IO.
- Implement smooth remote-player interpolation.
- Prevent movement outside room boundaries.
- Server validates movement and room transitions.
- Handle player disconnects and reconnections.
- Avoid duplicate or ghost avatars.

### 2.3 Room System

The application contains exactly five rooms:

1. The Lobby — default spawn location.
2. Pawffice — shared workspace.
3. Mewting Room — meeting area.
4. Catfé — casual hangout area.
5. Catnap Corner — relaxation area.

Requirements:

- Players can move between rooms.
- Provide a simple room navigation interface.
- Room transitions must update multiplayer presence.
- Players only see other players in their current room.
- Display the number of online players per room.
- Room state is managed by the server.
- All rooms are predefined and stored in memory.

### 2.4 Realtime Text Chat

- Implement text chat using Socket.IO.
- Messages appear immediately without refreshing.
- Chat is isolated by room.
- Display sender nickname and timestamp.
- Preserve a limited recent message history in memory.
- Validate message length and content.
- Apply basic message rate limiting.
- Prevent HTML/script injection.
- Messages must not appear in other rooms.

### 2.5 Voice Call

Use LiveKit for WebRTC audio communication.

Requirements:

- Players can join voice communication in their current room.
- Voice is isolated between rooms.
- Provide microphone mute/unmute controls.
- Show microphone connection status.
- Show an indicator when another player is speaking.
- Support microphone permission handling.
- Handle microphone/device errors gracefully.
- Switching rooms must disconnect from the previous voice room.
- Never connect players to multiple voice rooms simultaneously.
- LiveKit access tokens must be generated by the backend.
- Never expose LiveKit API secrets in frontend code.
- Voice should be opt-in; do not automatically activate microphones.

Video/facecam is explicitly excluded from v0.1.

### 2.6 Invite System

- Users can invite friends using a shareable URL.
- Opening the URL should allow a new user to join the application.
- Support joining a specific room through the URL.
- Validate room identifiers.
- No authentication system is required for v0.1.
- Invite links are not security credentials; rooms are public to anyone with access to the application.

## 7. REALTIME BEHAVIOR

Implement these behaviors correctly:

**Player joins**
- Server assigns or validates a session identity.
- Player enters the Lobby unless a valid room is specified.
- Existing players receive a join notification.
- New player receives the current room snapshot.

**Player moves**
- Client sends movement input or updates.
- Server validates movement.
- Server broadcasts authoritative state.
- Other clients interpolate movement.

**Player changes room**
- Server validates target room.
- Player leaves the previous Socket.IO room.
- Player joins the new Socket.IO room.
- Client receives the new room snapshot.
- Chat context changes.
- Previous voice connection is terminated.
- New voice connection requires appropriate user consent and a fresh room-scoped token.

**Player disconnects**
- Server removes player presence.
- Other players receive the update.
- Client cleans up voice and socket resources.

**Player reconnects**
- Restore the session safely when possible.
- Avoid duplicate players.
- Resynchronize room state.

## 8. SECURITY AND RELIABILITY

## 10. ACCEPTANCE CRITERIA

The implementation is considered complete only when the following scenarios work.

**Test 1 — Multiplayer**

Open two browser sessions with different nicknames.

Both players must see each other's avatars moving in realtime.

**Test 2 — Room Isolation**

Move Player A to Pawffice and Player B to Catfé.

They must not see each other's avatars.

**Test 3 — Realtime Chat**

Both players join the same room.

Messages must appear in both browsers immediately.

**Test 4 — Chat Isolation**

Move one player to another room.

Messages from the original room must not appear in the other room.

**Test 5 — Voice Call**

Both players join the same room and explicitly enable voice.

They must be able to communicate through their microphones and speakers.

**Test 6 — Voice Isolation**

Move one player to another room.

The previous audio connection must stop.

**Test 7 — Reconnection**

Refresh or temporarily disconnect a browser.

The application must recover without leaving duplicate avatars.

**Test 8 — Invite Link**

Copy a room invite link and open it in another browser.

The new player must enter the correct room.

**Test 9 — Error Handling**

Disable microphone permissions or stop the LiveKit server.

The game must remain usable for multiplayer and text chat.

**Test 10 — Windows Compatibility**

All development commands must work in PowerShell without requiring Linux, WSL, Docker, or Podman.
